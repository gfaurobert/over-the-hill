## Architecture Slop Priorities

| id | title | category | severity (1-10) | confidence | evidence paths | rationale |
|---|---|---|---:|---|---|---|
| ARCH-001 | Missing explicit error taxonomy across auth/session/data/privacy boundaries | Missing domain errors | 10 | High | `components/AuthProvider.tsx`, `lib/services/sessionValidationService.ts`, `app/api/auth/validate/route.ts`, `app/api/auth/refresh/route.ts`, `lib/services/supabaseService.ts`, `lib/services/privacyService.ts` | Core flows span multiple trust boundaries, but architecture docs show no shared domain error model (e.g., `SessionExpired`, `SessionRefreshFailed`, `EncryptionUnavailable`, `OwnershipViolation`, `ImportConflict`). Without typed/semantic errors, failures collapse into generic messages and recovery logic becomes branchy and inconsistent. **Action:** define a small discriminated error union and enforce translation at each boundary. |
| ARCH-002 | Silent-failure risk from multi-layer fallback chains (crypto + cache + offline) | Silent failures | 9 | Medium-High | `lib/services/privacyService.ts`, `lib/services/cacheService.ts`, `public/sw.js`, `lib/services/simpleDataService.ts`, `lib/services/supabaseService.ts` | Architecture explicitly uses fallback behavior (RPC/client crypto fallback, storage fallback, service-worker exclusions). If fallback outcomes are not surfaced as first-class signals, the app can degrade silently (stale reads, weaker privacy mode, partial persistence) while appearing successful. **Action:** emit structured degraded-mode outcomes (not booleans) and route them to UI/telemetry. |
| ARCH-003 | Inconsistent error propagation between client provider, service facades, and API routes | Mismanaged propagation | 9 | Medium-High | `components/AuthProvider.tsx`, `lib/services/sessionValidationService.ts`, `lib/services/simpleDataService.ts`, `lib/services/cachedDataService.ts`, `app/api/auth/validate/route.ts`, `app/api/auth/refresh/route.ts` | Session flow crosses provider -> client service -> API route; data flow crosses UI -> facade -> Supabase service. With no documented propagation contract, errors may be swallowed, rethrown generically, or converted to nullable returns depending on layer. **Action:** standardize one boundary contract (`Result<T, DomainError>` or throw-only + mapper) and forbid mixed patterns. |
| ARCH-004 | Import/export pipeline likely lacks partial-failure semantics | Missing domain errors | 8 | Medium | `components/HillChartApp.tsx`, `components/PrivacySettings.tsx`, `lib/services/supabaseService.ts#importData` | Import is batched across collections/dots/snapshots with encryption/upserts; this is failure-prone by nature. Without an explicit partial-success model (`created`, `updated`, `skipped`, `failed`) and resumability semantics, control flow can report success with hidden data loss or stop without actionable recovery. **Action:** add import report object and explicit retryable/non-retryable classifications. |
| ARCH-005 | Unused dual-service architecture (`simple` vs `cached`) increases error drift | Premature abstraction | 8 | High | `lib/services/simpleDataService.ts`, `lib/services/cachedDataService.ts`, `components/HillChartApp.tsx`, `components/PrivacySettings.tsx`, `components/ImportDataPrompt.tsx` | Two near-identical facades can diverge in exception wrapping/nullability semantics over time, causing behavior differences that look like random bugs. **Action:** choose one runtime facade and delete/archive the other to keep one error contract. |
| ARCH-006 | Auth refresh/validation loop lacks explicit retry budget and terminal states | Mismanaged control flow | 8 | Medium | `components/AuthProvider.tsx`, `lib/services/sessionValidationService.ts`, `app/api/auth/validate/route.ts`, `app/api/auth/refresh/route.ts` | Multi-step validate/refresh orchestration can oscillate when network/auth states flap unless terminal states are explicit (`force_logout`, `backoff_pending`, `reauth_required`). **Action:** codify retry budget + state machine transitions and map each terminal state to UX action. |
| ARCH-007 | Cache subsystem breadth can mask cache-write/cache-invalidate failures | Silent failures | 7 | Medium-High | `lib/services/cacheService.ts`, `lib/services/cacheInvalidationRules.ts`, `lib/services/cachedDataService.ts`, `public/sw.js` | Large cache API/rules surface combined with multiple cache layers makes it easy to treat invalidation or persistence failures as non-events, leading to stale UI that appears valid. **Action:** treat cache operations as observable outcomes (`applied`, `missed`, `failed`) and expose diagnostics in dev/test. |
| ARCH-008 | SSR mock cache adapters risk diverging failure semantics from browser runtime | Mismanaged propagation | 6 | High | `lib/services/cacheService.ts`, `lib/services/cachedDataService.ts` | Duplicated SSR no-op adapters can return success-like behavior where browser runtime would fail or degrade, hiding defects until production. **Action:** centralize one SSR adapter and mirror browser error/degraded semantics as closely as possible. |
| ARCH-009 | "Class + singleton + bound exports" obscures ownership of throw/catch boundaries | Indirection without leverage | 6 | High | `lib/services/simpleDataService.ts`, `lib/services/cachedDataService.ts` | Multiple invocation styles make it harder to reason about where errors are normalized and where stack context is preserved. **Action:** flatten to one export style and keep boundary mappers explicit. |
| ARCH-010 | Placeholder options/no-op API paths can imply successful handling when none occurred | Silent failures | 5 | High | `lib/services/simpleDataService.ts` | Empty option types and no-op cache methods create "accepted but ignored" calls, which are semantically close to silent failure for callers expecting behavior. **Action:** remove or deprecate with explicit runtime warnings. |
| ARCH-011 | Cache invalidation rule set includes non-active operations, diluting failure signal clarity | Indirection without leverage | 4 | Medium | `lib/services/cacheInvalidationRules.ts`, `lib/services/cachedDataService.ts`, `lib/services/cacheService.ts` | Extra rule surface increases ambiguity when debugging invalidation misses because many branches are theoretical. **Action:** prune to active mutations and add rules only with corresponding runtime use. |

## Suggested execution order

1. Define and adopt a shared domain error taxonomy and boundary mapping (`ARCH-001`, `ARCH-003`).
2. Add explicit degraded-mode/partial-failure outcomes for fallback-heavy and import flows (`ARCH-002`, `ARCH-004`).
3. Formalize auth/session state machine with retry budgets and terminal outcomes (`ARCH-006`).
4. Collapse to one runtime data facade and simplify throw/catch ownership (`ARCH-005`, `ARCH-009`).
5. Tighten cache/error observability and remove semantics-masking dead paths (`ARCH-007`, `ARCH-008`, `ARCH-010`, `ARCH-011`).
